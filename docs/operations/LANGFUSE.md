# Трассировка Langfuse

Используется Python SDK Langfuse 5.1.0 (версия зафиксирована в `uv.lock`).
Трассировка включается при наличии всех трёх переменных:

```dotenv
LANGFUSE_PUBLIC_KEY=pk-lf-...
LANGFUSE_SECRET_KEY=sk-lf-...
LANGFUSE_BASE_URL=https://cloud.langfuse.com
LANGFUSE_TRACING_ENVIRONMENT=development
```

Укажите адрес своего региона Langfuse Cloud или собственного сервера.
Ключи создаются в настройках проекта Langfuse; передавайте их через окружение
или локальный env-файл. Не добавляйте реальные ключи в Git или сообщения.
Приложение не проверяет доступность Langfuse при старте: экспорт идёт в фоне,
недоступность сервера не блокирует ответы пользователям.

Без полного набора переменных трассировка отключена. Для явного отключения
задайте `LANGFUSE_TRACING_ENABLED=false`. Дополнительно SDK поддерживает
`LANGFUSE_SAMPLE_RATE` (0–1) и `LANGFUSE_RELEASE` (версия/commit приложения).
Для production задайте `LANGFUSE_TRACING_ENVIRONMENT=production`.

Локально после установки зависимостей (`uv sync --frozen`) перезапустите API и worker.
В Docker Compose env-файл читается при создании контейнера: после обновления
его настроек нужен `docker compose up -d --build --force-recreate api worker`.
Перезагрузка исходников через `--reload` не обновляет окружение контейнера.

## Что видно в Langfuse

Один trace `handle-message` соответствует одному обработанному сообщению.
Вход — очищенная реплика пользователя, выход — ответ ассистента.
Внутренние UUID пользователя и диалога задают `user_id` и `session_id`;
теги `message` и канал (`website`, `telegram`, `avito`) помогают фильтровать запросы.
В Sessions сообщения одного диалога группируются вместе.

- `retrieve-context` (`retriever`): текущий запрос, пороги и найденные фрагменты
  со scores. Пустой список означает отсутствие контекста.
- `decide-lead`: решение AG2; повторная коррекция намерения помечена
  `force_lead_intent_confirmation=true`.
- Вложенные `generation` официальной OpenAI-интеграции: фактические сообщения
  модели, её ответ, модель, время, токены каждого вызова. Они учитываются
  непосредственно из ответа провайдера, независимо от `EVAL_CAPTURE_TOKEN_USAGE`.
- Metadata корневого span: текущее, предложенное и итоговое состояния,
  отклонение старта квалификации, готовность нового лида и успешный commit.
- `enqueue-lead` (`tool`): постановка готового лида в очередь. Это подтверждает
  только enqueue; доставку в CRM проверяйте по сохранённому статусу лида.
- `process-lead-delivery`: выполнение задачи Celery, task ID, номер retry,
  выбранный провайдер и итоговый статус лида.
- Вложенный `deliver-lead` (`tool`): предыдущий и итоговый статусы, CRM-адаптер,
  успешный commit, ошибки и пропуск уже доставленного лида.

Сообщение только с контактом пропускает retrieval, но вызывает основной LLM.
Ошибки провайдера, пустой/невалидный ответ и privacy-блокировки видны как
`ERROR`/`WARNING`; fallback дополнительно помечен в metadata.

## Приватность и ограничения

Аргументы и возвращаемые объекты функций автоматически не записываются.
Перед экспортом SDK очищает все атрибуты span через существующий `PiiSanitizer`:
телефоны, email и Telegram заменяются токенами. Если анализ завершился с ошибкой,
весь batch телеметрии отбрасывается. Ошибки приложения сохраняются как название
класса, без текста исключения и OTel exception events.
Публичные контакты БЗ восстанавливаются только для ответа API; в телеметрии они
также маскируются.

Это фильтр поддерживаемых контактных данных, а не универсальный детектор
секретов или любых персональных данных. Очищенные реплики, история, контекст RAG
и ответы модели уходят на заданный сервер Langfuse; имена, адреса и произвольные
конфиденциальные сведения могут сохраниться. Выбирайте размещение и срок хранения
Langfuse с учётом содержимого диалогов.

SDK не раскрывает скрытое рассуждение модели. При остановке API вызывается
`shutdown()` в отдельном потоке, чтобы отправить накопленные spans.

## Celery worker

API передаёт в заголовке Celery `traceparent`: trace ID, ID span `enqueue-lead`
и флаг sampling. Worker продолжает эту трассу, даже если запрос API уже завершён.
Тело задачи по-прежнему содержит только UUID лида; контакты, CRM payload, baggage
и ключи через заголовок трассировки не передаются. Пользователь и сессия берутся
из PostgreSQL, а не из заголовков задачи.

Задача, отправленная напрямую через `deliver_lead.delay(lead_id)` без заголовка,
получает отдельную трассу. Невалидный `traceparent` игнорируется. При автоматическом
retry Celery сохраняет заголовок: попытки видны в одной трассе с общим task ID
и разными значениями `retry`.

SDK создаётся лениво внутри исполняющего процесса после prefork и переиспользуется
следующими задачами. После каждой задачи, включая ошибку перед retry, вызывается
`flush()`; сбой flush не вызывает повторную доставку. При штатной остановке worker
вызывается `shutdown()`. При SIGKILL незавершённый span может потеряться.

`delivered` в output записывается после успешного commit в PostgreSQL.
`delivery_failed` и `needs_review` отражают сохранённый бизнес-исход; статус
ошибки span содержит только класс исключения. Тексты ошибок CRM и контактный
payload в трассу не записываются. Для fake-провайдера `delivered` подтверждает
доставку в заглушку, а не во внешнюю CRM.

## Проверка

Тесты принудительно отключают внешний Langfuse. В `tests/unit/test_tracing.py`
реальный SDK экспортирует данные в память: проверяются очистка PII,
fail-closed поведение, fallback, ошибки и независимые токены/родители при
параллельных вызовах AG2 с HTTP-заглушкой.
Также проверяются продолжение трассы в задаче Celery, сохранение связи при retry,
задачи без заголовка/с повреждённым заголовком и безопасный сбой flush.

Для проверки настройки сервера отправьте синтетическое сообщение через
`POST /message` на API с временной базой `_test`/`_eval`. В Langfuse проверьте
вход/выход, Sessions, дерево наблюдений и токены generation. Не используйте
реальные контакты для smoke-теста.

Для проверки worker используйте отдельные Redis и временную PostgreSQL-базу
`_test`/`_eval`, `LEAD_DELIVERY_PROVIDER=fake` и одинаковые настройки Langfuse
в producer и worker. Запустите worker отдельным процессом с `--concurrency=1`,
поставьте `ready`-лид через `CeleryQueueClient.enqueue_lead_delivery()` и проверьте
в PostgreSQL `status=delivered`, отсутствие незавершённой попытки доставки и
дерево `enqueue-lead → process-lead-delivery → deliver-lead` в Langfuse.

[OpenAI-интеграция](https://langfuse.com/integrations/model-providers/openai-py),
[маскирование](https://langfuse.com/docs/observability/features/masking).
